# Catalog admission compliance

Self-audit against every rule in `plugin-catalog/README.md` (re-read in full in pass 3). Verdicts are about this repository at
the commit being submitted. Rules that are process, not code, say so. Automated checks live in
`tests/test_catalog_compliance.py`, and `hermes plugins validate .` is clean.

| # | Rule | Verdict |
|---|---|---|
| 1 | Human-merged gate | **Process.** Entry is submitted as one file, `catalog/pit-crew.yaml`, via PR to `hermes-agent`; nothing self-registers. |
| 2 | Exact SHA pins | **Compliant (in the catalog PR).** The 40-hex sha and the pinned image/screenshot URLs are filled in the catalog PR itself. The copy in this repo, `catalog/pit-crew.yaml`, is a template and keeps the placeholder sha (`0000…`) and `TODO-SHA`. |
| 3 | No self-updating code | **Compliant.** No code downloads, replaces or updates plugin files; no `subprocess`/`pip`/`urlretrieve` anywhere in the package (test). Third-party adapters are loaded only from *already installed* packages through an entry point, never fetched. The Desktop file is static and imports only the SDK. |
| 4 | SHA bumps are new PRs | **Process.** |
| 5 | Owner submission | **Compliant.** The repository is public, and the catalog PR is opened by the repository owner (`trevornk`). |
| 6 | Declared capabilities match reality | **Compliant.** `provides_tools` (6) and `provides_hooks` (3: `pre_tool_call`, `post_approval_response`, `pre_llm_call`) equal what `register()` registers (validator + `test_manifest.py`); no middleware; no `capabilities:` consent surfaces requested. `requires_env` is empty in both the manifest and the catalog entry on purpose: nothing gates loading on an env var. The optional secrets (HA / TeslaMate / Teslemetry-Tessie tokens) are declared as `config_schema` `secret` fields (rule 11's second route) and listed in the README and the PR body (`docs/PR_BODY.md`). |
| 7 | Install scanner | **Compliant.** `security scan — safe` (no `dangerous`, no `caution` findings). |
| 8 | Desktop stays inside the SDK | **Compliant.** `desktop/plugin.js` imports only `@hermes/plugin-sdk` and `react`; no `eval`/`new Function`, no `document`/`window` access, no `window.hermesDesktop`, no `data-slot` selectors, no hard-coded colors (test + `desktop surface` check). |
| 9 | No runtime overrides of Hermes core | **Compliant.** `no core override` check passes with no warnings; core imports are limited to documented modules (`plugins.plugin_storage`, `hermes_cli.config`, `hermes_cli.plugin_events`, `agent.secret_scope`). The one `sys.modules[...]` write is in the *fallback* path of `dashboard/plugin_api.py`: it registers **this plugin's own private package name** (`pit_crew_desktop_core`) so its relative imports resolve when the backend must load its own copy (the already-loaded package is used whenever there is one, e.g. under `plugins.isolation: host`). It never touches a core module; disclosed in `docs/PR_BODY.md`. |
| 10 | Dependency policy | **Compliant.** One dependency, `tesla-fleet-api>=1.5,<2` (oldest API-compatible floor — verified call-by-call against 1.5.0 and 1.21 — with an upper bound; Apache-2.0; imported lazily). CI (`.github/workflows/ci.yml`) applies a release-age quarantine (`uv --exclude-newer "3 days"`) to the **test tooling only**; the plugin's own dependency is not resolved in CI. Its resolution was checked once by hand under Hermes' installed pins with `pip install --dry-run -c <Hermes pins>` (no conflict), and catalog CI runs `validate --install-deps`. Note it pulls `bleak`/`protobuf`/`cryptography` transitively. |
| 11 | Credentials come through Hermes, never from files | **Compliant (pass 3).** Every secret — HA token, TeslaMate token, Teslemetry/Tessie token — is a declared `config_schema` secret read only by `agent.secret_scope.get_secret(NAME)` (`service.hermes_secret_getter`, the single credential route; a test pins this). No `os.environ`/`getenv`, `.env`, `auth.json`, keychain or token-file access. **Plugin-held Tesla OAuth was removed entirely**: no refresh-token storage or rotation, no token store file, no OAuth client, no signing-key reading. Tesla's Fleet API (own developer app) is supported through Home Assistant's official Tesla Fleet integration, which holds and refreshes the tokens. |
| 12 | Approvals and unattended runs respected | **Compliant (pass 8).** Approval-class commands escalate through Hermes' real gate (`pre_tool_call` → `approve`), follow the user's Hermes approval setting (asked when approvals are on; not asked when off/yolo); the Advanced `require_human_for` setting forces a recorded human *yes* for listed commands even then and refuses when no human answer is available. They fail closed when unattended; the plugin never auto-approves, never disables guards, never spawns Hermes/shell children. **The plugin's own pages can no longer approve anything**: for approval-class commands the Desktop and web pages only preview the policy checks and hand the request to Hermes (`host.composer.insertText`, or a copy-the-sentence helper on the web dashboard); `dashboard/plugin_api.py` `/command` refuses them while live (`status: ask_hermes`), and the old single-use UI tokens are no longer used for approval. Safe-direction and comfort commands (lock, close windows, Sentry on, climate, charging) still run from the page behind its confirm dialog, as the same commands do for the agent without a prompt. |
| 13 | Risky behaviour disclosed | **Compliant.** README "Privacy and risk disclosure" and the catalog description list: network calls (HA, TeslaMateApi, Teslemetry/Tessie via `tesla-fleet-api`), the background watcher, the SQLite store, optional alert push to a Hermes delivery target (Hermes' own cross-platform send), reads outside the plugin's data (a user-supplied custom HA profile path), that armed + approved it can unlock a real car, and that there is **no stored credential and no telemetry**. |
| 14 | Compatibility metadata truthful | **Compliant.** `requires_hermes: ">=0.23.0"` (SemVer, equals the installed release's floor, never newer) in both `plugin.yaml` and the entry; `version` `0.2.0` matches the code; dependencies resolve under Hermes' pins (see 10). `validate --install-deps` itself was not run here because it installs into the Hermes venv (outside the build's boundaries); catalog CI runs it. |
| 15 | No skins/forks of bundled plugins | **N/A.** Original plugin. |
| 16 | One listing per lineage | **N/A.** Original; not a fork. (Unrelated catalog entry `crew` exists; different name and purpose.) |
| 17 | No unscannable payloads | **Compliant.** No binaries, bytecode or archives are tracked (test inspects every tracked file's header and extension). |
| 18 | Password managers | **N/A.** No `browser_vault` login backend. |

## Things reviewers may want to look at

* The pages' hand-off to Hermes for approval-class commands (rule 12 note above).
* `dashboard/plugin_api.py`'s private `sys.modules` registration (rule 9 note).
* `adapters/profile.py` reads a user-chosen custom HA profile file (JSON/YAML; not credentials), disclosed under rule 13.
